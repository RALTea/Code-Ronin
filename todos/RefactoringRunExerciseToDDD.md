1. The Problem with the Current `runExercise.ts`

The `runExercise.ts` file acts as a "script" that orchestrates a complex process. It knows too much about:
*   **Fetching data**: It directly calls functions to get solutions, test cases, and task details.
*   **Domain Logic**: It contains the business rules for building the code to be evaluated (`_buildCodeToBeEvaluated`).
*   **Infrastructure**: It calls an evaluation service and knows how to parse its specific output (`OutputParser`).
*   **Side Effects**: It's responsible for triggering side effects through `successHandlers` and `failHandlers`.

Our goal is to separate these concerns into distinct layers as per DDD.

### 2. The Target Architecture: The `AttemptTask` Use Case

The existing `AttemptTask.usecase.ts` is the perfect place for the refactored logic. It should be the single entry point in our application layer for handling a task attempt. It will act as an orchestrator, delegating work to the domain and infrastructure layers.

Here is the proposed design:

#### a. The `AttemptTask` Use Case (Application Layer)

The `AttemptTaskUsecase` class will orchestrate the entire process. Its dependencies should be injected via the constructor, making them explicit and replaceable for testing.

**Dependencies:**
*   `ITaskRepository`: To load the `Task` aggregate.
*   `IAttemptRepository`: To persist the `Attempt` aggregate.
*   `ICodeBuilder`: A domain service to construct the code.
*   `ICodeEvaluationService`: An abstraction over the external code execution engine (e.g., Judge0).
*   `IEventDispatcher`: To publish domain events for side effects.

**Execution Flow (`execute` method):**
The `execute` method should be lean and descriptive of the process:

1.  **Receive Command**: It takes a simple command object: `AttemptTaskCommand = { apprenticeId, taskId, apprenticeSolution }`.
2.  **Load Aggregates**: Fetch the `Task` from the `ITaskRepository`.
3.  **Create Attempt**: Instantiate an `Attempt` aggregate: `const attempt = Attempt.create(apprenticeId, taskId, apprenticeSolution);`.
4.  **Build Code**: Delegate code construction to the `ICodeBuilder` domain service.
5.  **Evaluate**: Pass the code to the `ICodeEvaluationService`.
6.  **Process Results**: The `Attempt` aggregate itself should be responsible for processing the evaluation result. We can add a method like `attempt.processEvaluation(rawResult)`. This method would contain the logic from the old `OutputParser`, determine success/failure, and generate domain events.
7.  **Persist**: Save the updated `Attempt` aggregate using the `IAttemptRepository`.
8.  **Dispatch Events**: Use the `IEventDispatcher` to publish the events generated by the `Attempt` aggregate.
9.  **Return Result**: Return a simple DTO indicating the outcome.

#### b. `Attempt` Aggregate (Domain Layer)

This is the heart of our domain model for this use case. It's not just a data structure; it's an object with behavior that enforces business rules.

*   **`Attempt.create(...)`**: A static factory method to create a new attempt in its initial state.
*   **`processEvaluation(result)`**: This is a new, crucial method. It takes the raw output from the evaluation service, uses the parsing logic (moved from `OutputParser`) to interpret it, updates its own status (e.g., `isSuccess`), and records a domain event (e.g., `TaskAttempted`).
*   **Event Generation**: The aggregate should not dispatch events itself. Instead, it should collect them in an internal list. The application layer (the use case) will ask for these events and dispatch them.

#### c. Domain & Infrastructure Services

*   **`CodeBuilder` (Domain Service)**: The logic from `_buildCodeToBeEvaluated` should be extracted into its own stateless domain service. Its role is to transform a solution and test cases into a single piece of executable code.
*   **`ICodeEvaluationService` (Domain/Application Interface)**: Define an interface for the code evaluation service. The use case will depend on this abstraction, not a concrete implementation.
*   **`Judge0EvaluationService` (Infrastructure Implementation)**: The concrete implementation that calls the Judge0 API will live in the infrastructure layer. It will implement `ICodeEvaluationService`.

#### d. Handling Side Effects with Domain Events

The `successHandlers` and `failHandlers` create tight coupling. A much cleaner approach is to use domain events.

1.  When the `Attempt` aggregate processes the evaluation, it creates an event like `TaskAttempted { attemptId, isSuccess, apprenticeId, taskId, expAwarded }`.
2.  The use case dispatches this event.
3.  Separate, focused **event listeners** subscribe to this event to handle side effects:
    *   `AwardExpOnSuccess`: Listens for successful attempts and updates the apprentice's EXP.
    *   `NotifyOnFailure`: Listens for failed attempts and sends a notification.
    *   ...and so on.

This decouples the core logic of attempting a task from what happens *after* the attempt is finished.

### Summary of Refactoring Steps

1.  **Enhance `AttemptTask.usecase.ts`**: Make it the central orchestrator, injecting repositories and services.
2.  **Flesh out the `Attempt` Aggregate**: Move the result-parsing and status-determining logic into a `processEvaluation` method on the aggregate. Have it generate domain events.
3.  **Create a `CodeBuilder` Domain Service**: Extract the code-building logic from `runExercise.ts`.
4.  **Abstract Infrastructure**: Create an `ICodeEvaluationService` interface and move the implementation to the infrastructure layer.
5.  **Replace Handlers with Events**: Remove the `successHandlers` and `failHandlers` in favor of a domain event like `TaskAttempted` and create corresponding event listeners.

By following this design, you will have a system that is more aligned with DDD principles, easier to understand, more resilient to change, and significantly easier to test.
